# Providers beyond Hetzner (`PROVIDER=other`)

What differs on a dedicated server (or any VPS outside Hetzner), what this setup does about it,
and where each provider keeps the OS install, the rescue system, the out-of-band console, its
firewall and its backup space. Phase 01 ("Other provider") and phase 02 step 4 point here.

Nothing in this setup drives a provider's API: the user installs the OS in the panel (or with the
API themselves), the agent checks the box (`server_check`) and puts the firewall on it
(`vps-hostfw`). Provider-specific firewall and backup steps are only on request (`ROADMAP.md`
R20).

**How sure this is.** None of it has been run on a dedicated server yet. Everything marked
**[verify]** comes from the providers' documentation as read while planning, or is an assumption,
and has not been checked against a real panel; the doc pages named in each section are where to
check it. Panels change their wording; when the user sees something else, ask them what they see
and adapt.

## What differs on a dedicated server

| | Hetzner Cloud (`PROVIDER=hetzner`) | Another provider (`PROVIDER=other`) |
|---|---|---|
| The server | `hcloud server create` (phase 01) | the user orders it and installs Ubuntu 24.04 with their key in the panel or by API; phase 01 checks it (`server_check`) |
| Firewall | Hetzner Cloud Firewall `vps-setup-fw`, in front of the server | `vps-hostfw` on the server: `INPUT` and Docker's `DOCKER-USER`, IPv4 and IPv6 (phase 02 step 4) |
| Locked out | Hetzner Console, Rescue | the provider's rescue system or out-of-band console (KVM over IP, iDRAC, iLO, IPMI) |
| Whole-disk backups | Hetzner backups, snapshots | none from this setup; the provider's backup space (often FTP or NFS) by hand |
| Database backups | S3 (Hetzner Object Storage) | the same, any S3-compatible bucket (phase 06 step 1) |
| Billing | by the hour, delete and it stops | a monthly contract, often a setup fee and a notice period |
| Disks | one virtual disk | usually two: software RAID-1, set in the installer |

## The host firewall (`vps-hostfw`)

Docker publishes container ports by writing its own iptables rules, and that traffic never
reaches `ufw`'s rules. Docker's documentation names the place for a firewall of one's own: the
`DOCKER-USER` chain, evaluated before Docker's own forwarding rules. `vps-hostfw` (generated by
`hostfw_script` in `lib.sh`, installed to `/usr/local/sbin/vps-hostfw`) uses it:

| Rule | Why |
|------|-----|
| every rule has `-i <public iface>` (the IPv4 default route's interface, or `IFACE` in `/etc/vps-hostfw.conf`) | traffic between containers (`docker0`, `br-*`), from containers out and to the host over a bridge is never matched |
| every rule carries the comment `vps-hostfw` | status and revert find exactly ours; other rules are never deleted, no chain is flushed, no policy changes |
| `INPUT`: ICMP, replies (`ESTABLISHED,RELATED`), TCP `PORTS`, DHCP replies, then `DROP` | the host's own services; ICMPv6 must pass or IPv6 neighbour discovery breaks |
| `DOCKER-USER`: replies, `-m conntrack --ctorigdstport <port> --ctdir ORIGINAL` per port, then `DROP` | Docker has rewritten the destination already (DNAT) when the packet arrives, so the published port is the connection's original destination port |
| `PORTS="22 80 443"` (plus `hostfw_port_add` ones) | the same ports as the Hetzner cloud firewall (`FIREWALL_EXPECT`); UDP 443 (HTTP/3) stays closed on both |
| `apply --trial`: `systemd-run --on-active=300 ... revert` before the first rule | if the new rules cut SSH, they remove themselves after five minutes |
| refuses when sshd's port is not in `PORTS`, the default route is unclear, IPv6 uses another interface, or Docker runs its nftables backend | each would lock out or guard nothing |
| `vps-hostfw.service` (oneshot, `After=docker.service`, `PartOf=docker.service`) applies the confirmed config at boot | rules come back after a reboot and after a Docker restart; no `iptables-persistent`, which would also restore Docker's own chains before Docker |

Seen on an Ubuntu 24.04 Coolify server with Docker 29.1.3, 2026-10-20: `docker info --format
'{{.FirewallBackend.Driver}}'` prints `iptables` (Docker 29's default backend), and `iptables
--version` prints `iptables v1.8.10 (nf_tables)`, the nft-backed iptables of Ubuntu 24.04.
`vps-hostfw` refuses when the field says `nftables`, and also when it is empty or missing
(unknown) on a box with Docker.

Still **[verify]** on a real box:

- conntrack's `--ctorigdstport` and `--ctdir` with that iptables (not checked yet).
- Docker keeps the content of `DOCKER-USER` when it restarts and only re-adds the jump from
  `FORWARD`, and it adopts a `DOCKER-USER` chain made before Docker was installed (phase 02 runs
  before phase 03 installs Docker). The checkup notices either failure (`CHECKUP.md` 3a), and the
  boot unit re-applies after every Docker restart.
- The default-route interface is the public one at each provider (bonding or a VLAN, OVHcloud
  vRack, Scaleway RPN may differ), and IPv6's default route is on the same interface.
- `systemd-run --on-active` and `--timer-property=AccuracySec=` behave as expected on the
  providers' Ubuntu images.
- A few seconds at boot between the network and the unit are unfiltered.

## Scaleway Dedibox

Docs: Scaleway documentation, Dedibox section (docs.scaleway.com, source repo
`scaleway/docs-content`); the Dedibox console is console.online.net. All **[verify]**:

- **OS install:** Scaleway console → **Bare Metal** → **Dedibox** → the server → **Install**
  (or reinstall): the type and version of the OS, partitioning (filesystems, software RAID 0/1/5),
  then the server name, a username, a password and the SSH key. The install may take about 20
  minutes; the docs suggest waiting longer before the first login. A reinstall deletes all
  data. Which Ubuntu versions are listed: check that 24.04 is.
- **Login user:** the username chosen at install, not root: phase 01 step 2 copies the key to root.
- **Rescue:** pick a rescue OS and **Boot in rescue mode**; it uses the SSH keys registered for the
  server; back with the switch to normal mode on the overview page.
- **Out-of-band console:** KVM over IP per model (Dell iDRAC, HP iLO, Supermicro, Quanta,
  ASRockRack): Dedibox console → **Server** → **Server list** → **Manage** → **iDRAC**/**iLO**, after
  entering the IPv4 address allowed to connect (IPv4 only). Session length: unknown.
- **Firewall:** no network firewall for Dedibox found in the docs; Anti-DDoS included. The host
  firewall is the only one.
- **Backup space:** Dedibackup, an FTP space reachable only from the Dedibox network (100 GB
  included, a bigger option). Not S3: the off-site database backups still go to an S3 bucket
  (Scaleway Object Storage, endpoint `s3.<region>.scw.cloud`).
- **API:** console.online.net/en/api/, a bearer token; install, rescue boot and normal boot have
  their own calls. Not used here.

## OVHcloud dedicated servers (Advance)

Docs: OVHcloud guides, Bare Metal Cloud → Dedicated servers (docs.ovhcloud.com). All **[verify]**:

- **OS install:** Control Panel → **Bare Metal Cloud** → **Dedicated servers** → the server →
  **General information** → `...` next to the OS → **Install my server** / **Reinstall my
  server**; the SSH key in the install form; custom partitioning possible; by default all disks,
  RAID 1. The Ubuntu template's name: check that 24.04 is offered.
- **Login user:** OVHcloud's Ubuntu templates may log in as `ubuntu` rather than root: phase 01
  step 2.
- **Rescue:** **General information** → `...` next to **Boot** → **Edit** → **Boot in rescue
  mode** (password by email or the SSH key), then a reboot; afterwards back to **Boot from the
  hard disk**.
- **Out-of-band console:** tab **IPMI/KVM**: an HTML5 KVM in the browser, a Java KVM, Serial over
  LAN; may be limited on the cheaper ranges. Present on Advance: check.
- **Firewall:** the Edge Network Firewall, per IP under **Network** → **Public IP Addresses**:
  stateless, IPv4 only, at most 20 rules, forced on during DDoS mitigation. A possible second
  layer on request; the host firewall stays the one this setup checks.
- **Backup space:** tab **Backup Storage** → enable: FTP, NFS or CIFS, reachable only from the
  account's IPs, does not back anything up by itself. Included size: check.
- **API:** `/dedicated/server/{serviceName}/install/compatibleTemplates`,
  `/dedicated/server/{serviceName}/reinstall` and the task calls. Not used here.

## Servers.com (Enterprise Bare Metal)

Docs: servers.com/docs (EBM, VPN to OOB, firewall) and developers.servers.com (API v1). All
**[verify]**:

- **OS install:** the customer portal → **Enterprise Bare Metal** → **Order**: OS, SSH key and/or
  password, user data, RAID; a reinstall call exists in the API.
- **Login user:** root or another: check on the first install.
- **Rescue:** not found in the docs read; check.
- **Out-of-band console:** iDRAC through a free "VPN to OOB"; the OOB credentials come from the
  API encrypted to a GPG key an account owner uploads.
- **Firewall:** a separate stateful firewall product with its own VLAN; limits and price: check.
  The host firewall stays the one this setup checks.
- **Backup space:** check.

## Worldstream

Docs: Worldstream knowledge base; the portal is portal.worldstream.com. All **[verify]**:

- **OS install:** portal → **Bare Metal** → the server → **Installation** → **Reinstall Operating
  System**, an OS from the catalogue (Ubuntu 24.04 is named as an example), a root password
  (save it before confirming); destroys all data. An SSH key at install: check.
- **Login user:** root.
- **Rescue:** the documented ways back are a reinstall or a support ticket; a self-service rescue
  boot: check.
- **Out-of-band console:** Dell iDRAC, HP iLO or IPMI depending on the hardware, only over the
  **Remote Access** VPN from the server's **Remote Access** tab; HTML5 console, virtual media.
- **Firewall:** DDoS protection included; a firewall product: check.
- **Backup space, API for a reinstall:** check.

## Any other provider

The same questions, asked before ordering: can the panel install Ubuntu 24.04 with my SSH key,
which user logs in, is there a rescue system and an out-of-band console (and does it need a VPN),
is there a firewall in front of the server (not needed here; the host firewall is), what does
the notice period look like.
